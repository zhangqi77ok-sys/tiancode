# ADR-0007：审批闸门（opt-in，默认关闭）

- 状态：已采纳（**部分修订 ADR-0005 中"拦截型护栏 MVP 一律不进"**）
- 日期：2026-09-24
- 关联：ADR-0005（设计模式取舍）、`docs/CONTRACTS.md`（C-APR-*）

## 背景

agent 能执行 shell 命令与写文件。用户事前无法确认"这条命令是否真的要跑"。
旧项目曾用 `astguard`（写前 AST 检查）做自动拦截，结果**误杀正常写入**——
因为它替用户做判断，判错了既阻断工作又难以解释。

现在要引入"执行前确认"，必须证明它不会重演 astguard 的失败。

## 决策

引入 **Approver 端口**（Strategy，非拦截链）：agent 在执行工具前询问一次，
**由用户显式决定**，而非由代码猜。

```
agent.execTool 之前
  → Approver.Review(ctx, ApprovalRequest{ToolName, Arguments})
      → 决策来自 UI 的显式操作（允许 / 拒绝）
  → 允许 → 正常执行；拒绝 → ToolResult{IsError:true, Content:"用户拒绝执行…"}
```

### 五条硬约束（每条都对应 astguard 的一个失败面）

1. **默认关闭**：未配置审批工具清单时 `Approver` 为 nil，行为与现在完全一致。
   （astguard 的错在于"默认开 + 猜"。）
2. **不做内容分析**：只看"工具名是否在清单内"，绝不解析命令/代码语义。
   （astguard 的错在于用 AST 猜用户意图。）
3. **拒绝要可见且可解释**：拒绝产生一条模型可见的工具失败结果（含原因），
   agent 可以据此改道；**绝不静默拦截**（静默 = 用户以为跑了/以为没跑，两种都糟）。
4. **等待审批受 ctx 约束**：取消或超时 → 视为拒绝并说明原因，绝不永久挂起。
5. **最小清单**：默认建议只纳入有副作用的工具（`shell`）；`fs` 写入不默认纳入
   （已有原子写 + 唯一性校验 + diff 预览三层可见性）。

### 与 ADR-0005 的关系

ADR-0005 禁的是 **Decorator/Hook 拦截链**（多个隐藏拦截器串起来、代码替用户做判断）。
本 ADR 引入的是**单一显式端口 + 用户决策**，变化点是"用户是否要在执行前确认"，
不是"代码要不要偷偷拦"。故保留 ADR-0005 其余结论，仅豁免此一项。

## 被否方案

- **AST/正则自动拦截**（旧 astguard）：误杀、无法解释、默认开——三重失败。
- **全部工具都审批**：日常读文件/查 git 也要点确认，交互成本高到用户会去关掉它。
- **审批后再写回账本才执行**（两阶段提交）：过度设计，当前无跨进程一致性需求。

## 代价与验证

- 代价：多一个端口 + UI 一个卡片；开启后每命令多一次点击（这是用户自己选的）。
- 验证：`core/agent` 的允许/拒绝/无审批器/取消四条用例；`internal/app` 的
  "等待-解决"配对用例（含未知或已处理 ID **一律拒绝**——重复提交时用户会看到明确提示，
  而不是"点了没反应"或"悄悄放行"）。
