# 任务清单闭环设计（三档）

> 日期：2026-10-04 ｜ 状态：**待用户审阅**（未写一行代码）
> 范围：把"任务清单"从给模型看的提示文本，变成系统持有、可跨轮、可核验的状态。
> 依据：用户在四项症状上全部勾选（假进度/不遵守、跨轮失忆、漏项/假完成、要人工续跑）。

---

## 零、诊断：四项症状是一个根因

**已核实的事实**（非推断）：

| 事实 | 位置 |
| --- | --- |
| `EventTodo` **已经落账本** | `internal/core/session/todo.go:6` |
| `deriveMessagesWith` 的 `projectEvent` **没有 `case session.EventTodo`** | `internal/core/agent/derive.go:178-333` |
| 因此任务清单**从未进入模型上下文**，只活在给 UI 看的 Replay 投影里 | 同上 |
| 步数用尽一律问用户 | `internal/core/agent/ask.go:87` `continueAfterLimit` |
| `TodoItem` 只有 `Text` / `Status` 两个字段 | `internal/core/llm/port.go:89-92` |

**结论**：模型每轮开局看到的历史中"计划"是不存在的。所谓"清单不遵守"不是模型不听话，是它**压根不知道清单存在**；所谓"跨轮失忆"不是没存盘，是**存了但没喂**。

四项症状都是这一个根因的不同表现，因此三档设计的顺序就是修复顺序。

## 档位 1：把清单注入模型上下文

### 改哪里

`internal/core/agent/derive.go` 的 `projectEvent` 增加 `case session.EventTodo`。

### 四个必须遵守的实现约束

1. **不得设置 `lastAssistant`。** `flush()` 会把待执行的 `tool_calls` 并入 `lastAssistant` 指向的消息（`derive.go:155-159`）。若清单消息被当作 `lastAssistant`，下一次工具调用的参数会挂到清单消息上，历史变成"清单 + tool_calls"的畸形结构。现有 `EventUserEdit` 同样不设（`derive.go:179-193`），照抄这个纪律。
2. **只取最新一条。** `EventTodo` 是全量快照语义（`session/todo.go:3`），取最新即当前计划；逐条投影会浪费 token 并让模型看到过时的中间版本。
3. **追加到末尾，不原位投影。** 清单是"当前状态"而非"历史事件"。原位投影会让最终版计划前面堆着一串历史版本；追加到扫描结束后，位置落在最后一条 user 消息（当前轮）之后，模型一定看得到。
4. **必须在 fork 过滤之后取。** 现有扫描先 `session.ForkDropped` 再 `projectEvent`（`derive.go:369-372`），因此"从某条用户消息重跑"时被丢弃区间里的旧清单天然不会复活。**这条容易写错，必须有测试锁住。**

### 折叠免疫

五级折叠（`derive.go:399-425`）只作用于 `toolRefs` / `imageRefs` / `bodyRefs` 三个索引表，注入的清单消息不进其中任何一张 → **天然免疫**。

但这是"当前恰好成立"，不是显式保证。若将来有人把清单也登记进 `bodyRefs`，清单会被静默折成一行说明，而模型仍以为计划还在。**必须有一条测试显式锁住"极小预算下清单仍全文"。**

### 注入文本形态

```
[任务清单·当前] 你在本会话登记的计划（最新一次提交，共 2 项，已完成 0 项）：
1. [进行中] 补 EventTodo 注入
2. [待办] 加契约测试
开工前先对照本清单。状态变化时用 todo 工具重新提交**整张清单**（全量快照）。
```

### 两条未在需求里出现的决策（已定，供否决）

1. **清单全部 `done` 时仍然注入**，写明"全部完成，可收尾"。
   理由：模型需要知道"计划已清空"才不会继续找活干；若此时不注入，模型反而不知道任务已结束。
2. **无 `EventTodo` 的会话不注入**，派生结果与旧版逐字节一致。
   理由：零噪声。没登记过计划的项目，不该凭空多一段说明。

### 契约与验证

| 项 | 内容 |
| --- | --- |
| 契约 | **C-AGT-5**：账本存在 `EventTodo` 时，派生消息末尾必含最新清单全文，且仅一条 |
| 契约 | **C-AGT-6**：极小预算（`BudgetTokens=1`）下清单**不被折叠** |
| 契约 | **C-AGT-7**：无 `EventTodo` 的账本，派生结果与旧版逐字节一致（零噪声） |
| 契约 | **C-AGT-8**：清单消息不得携带 `tool_calls`（`lastAssistant` 未被污染） |
| 契约 | **C-AGT-9**：落在 fork 丢弃区间内的清单不得出现 |
| 测试 | `internal/core/agent/todoinject_test.go`（新建），对应 5 条锁定测试 |

### 副作用评估

- **prompt cache**：清单在**尾部**，系统提示（前缀）逐字不变，cache 命中率不受影响。与现有折叠行为（本来就改尾部）同量级。
- **token**：每轮增加约 `清单字数 × 1`。清单通常十几到几十项，可忽略。
- **`todoTrack` 是否退休**：档位 1 上线后，清单每轮都在模型眼前，`todoTrack` 那套"催模型重交快照"的补丁（`todo_track.go`）是否还需要，属实施阶段判断。**建议先保留**——它是跨轮催提交的唯一机制，档位 1 只解决了"模型看得见"，没解决"模型会更新"。

### 风险

近乎为零。不新增 IO、不改 schema、不改工具协议、不碰 UI。

## 档位 2：自主续跑（治"要人工续跑"）

### 现状

`agent.go:760-787`：步数用尽 → `continueAfterLimit` 经 `ask_user` 通道问用户 → 同意则重新计一段。大工程要人工点 N 次。

### 改法

步数用尽时，**先做一次无工具的自评调用**，让模型对着清单裁决三选一：

| 裁决 | 条件 | 行为 |
| --- | --- | --- |
| `done` | 清单全部 `done` | 直接走收尾总结，不再问用户 |
| `continue` | 有未完成项 + 有明确下一步 + **额度未耗尽** | 自主续一段 |
| `blocked` | 无明确下一步 / 反复失败 / **额度耗尽** | 问用户（保持现状） |

### 信任边界的硬约束

这几条是"AI 自己决定要不要继续"能成立的前提，缺一条就不能上：

1. **额度硬封顶**，由用户配置。额度是唯一的刹车，必须是整数上限而非软判断。
2. **默认 0（关闭）**。不配置就完全保持现有行为，零风险；用户显式开启才生效。
3. **自评调用必须不带工具**（`Tools: nil`，照 `agent.go:798` 收尾步的写法）。否则模型会"边自评边继续干活"，自评失去判断意义且步数失控。
4. **自评结果落账本**，可审计。
5. **每次自主续跑在 UI 可见**。绝不能悄悄跑——用户有权知道 AI 在自己判断。
6. **降级防自欺**：模型选 `continue` 但清单已全部 `done` → 强制降级为收尾。

### 配置落点

照 `SetContextBudget` 的既有模式（`agent.go:129-142`）：新增 `Loop.SetAutoContinueSegments(n)`，由装配层从配置折算注入。内核不读配置、不引入新事实源。

### 契约与验证

| 项 | 内容 |
| --- | --- |
| 契约 | **C-AGT-10**：自评调用不得携带工具定义 |
| 契约 | **C-AGT-11**：自主续跑累计段数不得超过配置额度，触顶必问用户 |
| 契约 | **C-AGT-12**：额度为 0（默认）时，行为与旧版**逐条等价**（仍问用户） |
| 契约 | **C-AGT-13**：清单全 `done` 时不得续跑 |
| 契约 | **C-AGT-14**：每次自主续跑产生一条可审计事件 |
| 测试 | `internal/core/agent/autocontinue_test.go`（新建） |

### 需要 ADR

**需要 ADR-0009**。理由：这一步把"是否继续"的决策权**从用户移交给模型**，是 ADR-0005（决策权在用户/内核无状态）方向的实质性变更，属架构性决策，必须留档。档位 1 不需要 ADR（不改守卫规则、不改分层）。

### 风险

- **模型可能一直选 `continue`** → 额度是唯一刹车，所以额度必须小（建议开启时也不超过 3 段）。
- **自评本身可能误判**：清单 `done` 了但实际没做完（这正是档位 3 要治的）。档位 2 会放大这个问题——它信任清单。**因此建议档位 3 在档位 2 开启额度之前落地**；档位 2 在额度=0（默认）时与旧版逐条等价、风险为零，所以「先发 2 再发 3」在默认配置下也安全，只是不建议长期开着额度而不做 3。

## 档位 3：客观核账（治"漏项/假完成"）

### 先说被否决的方案

直觉做法是给每项加 `verify` 命令，模型标 done 时系统去执行验证。**本设计否决它**：

- 等于**让模型自己出考题再自己判卷**。模型把 verify 写成 `grep -q TODO` 就永远绿。
- 要执行命令 = 引入副作用 + 走审批闸门，成本与风险都高。
- 可靠性和收益不成比例。

### 采用的方案：系统侧客观取证

判据只来自**系统自己的账本事实**，不依赖模型自觉，零新增 IO。

1. `TodoItem` 增加 `Files []string`（可空）——声明这一项预期改哪些文件。
2. Loop 执行工具时**本来就拿到了** `llm.ToolCall`（含 `Name` + `Arguments`）。解析 `fs` 的 `action ∈ {write, replace}` 取 `path`，即得**本轮真实写入文件集**。零额外 IO。
3. 模型调 todo 声明 `done` 时（`runTodo`，`todo.go:83`）核对：

| 情形 | 判定 |
| --- | --- |
| 标 done + 声明 files + 本轮全部写过 | 放行 |
| 标 done + 声明 files + 有文件本轮没写 | **拒绝**，回纠偏结果（`IsError=true`）要求重交 |
| 标 done + **未声明 files** | 放行（降级：假装不了就不验） |
| 标 pending/in_progress | 不核对 |

4. **路径归一**：Windows 大小写不敏感、相对/绝对路径混用，归一后再比对（可复用 `app` 层已有的 `sameDir` 思路）。

### 兼容性

旧账本的 `TodoItem` 无 `Files` 字段 → `json.Unmarshal` 缺失即 `nil` → 走"未声明 → 放行"分支 → **旧账本行为零变化**。

### 诚实声明（这条很重要）

**这个核账只能证明"文件被写过"，不能证明"改对了"。**

- 它治的是：声称做了、实际一个字节没动（假完成）。
- 它治不了：动了，但改错了方向、改漏了调用点、改出了新 bug。
- 后者只能靠跑测试/构建来判，属于另一个话题（结构化验证闭环），**不在本设计范围**。

不把"能验文件动过"包装成"能验正确性"。

### 契约与验证

| 项 | 内容 |
| --- | --- |
| 契约 | **C-AGT-15**：`TodoItem.Files` 缺失（旧账本）→ 不核对、不拒绝 |
| 契约 | **C-AGT-16**：声明 files 但本轮未写 → 拒绝 done 并要求重交 |
| 契约 | **C-AGT-17**：路径比对大小写不敏感、相对/绝对等价 |
| 契约 | **C-AGT-18**：核账只认**本轮**写入，跨轮写入不计入 |
| 测试 | `internal/core/agent/todoaudit_test.go`（新建） |

### 覆盖盲区（明说，不假装覆盖）

- **模型本轮完全不调 `todo` 时，核账不会触发。** 清单是上一轮提交的，`runTodo` 不会被调用，声明与实际的偏差不会被发现。这是本方案的结构性盲区。
  缓解：档位 2 的自评环节（`continue` 分支）可以顺带触发一次核对——但那属档位 2 的实现细节，不在本档承诺。
- **核账失败时模型可以重交一次"声明 files 写错了"的清单绕过。** 核账是纠偏手段不是强制闸门，模型重交一次即绕过。**它的价值在于让漏项在当场暴露一次，而不是杜绝漏项。**

### 风险

- **schema 变更**：`TodoItem` 是模型可见的工具 schema（`todo.go:31-50`）。加字段是**加法**，旧模型不填即降级放行，向后兼容。
- **可能误伤**：模型声明了 files 但通过别的手段（用户手动改、代码块应用）完成 → 会误判拒绝。缓解：错误信息写清"本轮未观察到对 X 的写入，若已由用户完成请重交清单并说明"，把判断权交还模型。

## 明确不做（划界，防止范围蔓延）

| 不做 | 理由 |
| --- | --- |
| 执行 `verify` 命令做验收 | 模型出题自己判卷，见档位 3 |
| 用摘要模型压缩清单 | 清单必须逐字精确（路径/行号不能错），`derive.go:26-28` 已因同类理由拒绝摘要模型 |
| 多 Agent 编排 / 子代理 | README 已列为规划项，独立子系统，不属本设计 |
| git 写操作（stage/commit/branch） | `gittool.go:221-238` 刻意只读，是既有裁决 |
| 把 `todoTrack` 改掉 | 档位 1 不治"模型会不会更新清单"，该补丁仍有用；待档位 1 走完实测后再评估 |
| 结构化测试/构建闭环 | 真实缺口，但属另一个设计（用户本次未勾选） |

## 待你裁决的两点

1. **自主续跑的默认额度**：我建议 **0（默认关闭）**，用户显式开启且上限不超过 3 段。理由是这是唯一把决策权交给模型的改动，保守起步。
2. **档位 3 是否要做**：它治的是四项里最难的一项（假完成），但要动模型可见的 schema。我判断值得做，但由你定。
