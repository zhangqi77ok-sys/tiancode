# 代码智能：编译诊断 + 文件大纲（codeintel）设计

日期：2026-10-05　状态：已批准（用户裁决"完成目标，并测试修复 bug"）
关联：本次评审结论"LSP 诊断是最大单点杠杆"；`docs/CONTRACTS.md` C-FS-8~11

## 目标

把"编辑→知道改没改对"的反馈回路从分钟级（等全量 build/门禁）压到秒级（写入回执内联）。
两个能力：

1. **编译诊断**：`fs.write` / `fs.replace` 落盘 `.go` 文件后自动对所在包做编译级诊断
   （含 `_test.go`），错误以内联文本回到当次工具结果——模型同一回合内自纠，
   不再"写完靠猜"。另有手动 action `fs.diagnose`。
2. **文件大纲**：action `fs.symbols` 输出文件的符号骨架（函数/方法/类型，带行号），
   模型定位代码从"多次 grep 试错"变成一次精读大纲——省的是上下文预算。

## 方案与取舍

**诊断引擎 = `go vet ./<pkg>`（子进程，cwd=工作区根）**，不用 gopls / 不 vendor
golang.org/x/tools：

- 本机与用户环境普遍没有 gopls（dev 机实测未装）；vendor x/tools 只为诊断不值。
- `go vet` 覆盖类型错误、语法错误、未定义引用，且**包含 _test.go**（`go build` 不查
  test 文件——测试文件恰恰是高频编辑对象）；printf/shadow 等分析器警告是白赚的。
- go build 缓存温热后单包秒级；冷启动大仓库可能超预算——超时**不阻塞写入**，
  明示"诊断超时"并给出手动重试出路。
- 非 Go module / `testdata` / `vendor` 下优雅降级（不执行、明说原因），绝不让
  诊断把一次成功的写入变成失败——**诊断是信息，不是闸门**。

**大纲引擎 = go/parser（.go，精确）+ 正则启发式（ts/js/py/md 等，标注"启发式"）**。

## 档位

- **档位 1（本批）**：自动内联诊断、`fs.diagnose`、`fs.symbols`。
- **档位 2（延后，需另行立项）**：定义/引用跳转。需要常驻 LSP 客户端（gopls）
  或 vendor x/tools/go/packages——协议握手（gopls 的 workspace/configuration 等
  反向请求必须应答）与进程生命周期管理是独立工程量，不与本批混装。

## 边界（诚实声明）

- 只证明"编译不过"，不证明"逻辑对"；逻辑靠测试（快捷命令/门禁）。
- 诊断引擎只在 **Go** 上工作；其他语言返回明确"暂无诊断引擎"。
- 自动诊断对 `.go` 且工作区有 `go.mod` 才触发；其余情形静默（不制造噪音）。

## 契约（登记于 CONTRACTS.md）

- C-FS-8：write/replace 成功后对 `.go` 自动诊断，错误内联；诊断失败/超时绝不改写
  写入的成功语义。
- C-FS-9：手动 `fs.diagnose`；干净 = 明说"无错误"；跳过 = 明说原因（非 module 等）。
- C-FS-10：`fs.symbols` 有界（≤300 条）；Go 精确、启发式必须标注。
- C-FS-11：诊断/大纲输出 path:line 可点（与既有 outputRows 链路同源，前端零改动）。
